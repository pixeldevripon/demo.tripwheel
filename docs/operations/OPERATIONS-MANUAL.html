01

Orientation

What You Are Running Both

Island Tours is a Caribbean tour marketplace operating as a reseller: operators list single-day tours, travellers book instantly, the platform earns commission. Technically it is one API that owns a database, and front ends that own nothing.

That sentence is the whole architecture, and almost every operational rule in this manual follows from it. There is exactly one Prisma client in the system. The two Next.js applications have no DATABASE_URL and cannot reach Postgres even if they wanted to — every read and write they perform is an HTTP call to the API. So there is one thing to back up, one thing to migrate, one thing to secure, and one place where data can be corrupted.

Two apps, not three

There used to be a standalone tripwheel-app carrying the system-admin door. It was merged into the dashboard at /admin and deleted. Older runbooks describe a third Vercel project, a third PM2 entry and ports 3002/3102. On the demo those have no counterpart — where this manual marks a section Prod, that three-app world is what it means.

The shape of one request

Request path — everything public enters through one door

Client Public edge Application Data Background

Postgres and Redis publish nothing to the internet. The proxy is the only public entrance, and it forwards to a loopback port.

What that buys you operationally

  • One backup target. The postgres-data volume is the entire persistent state.
  • One migration path. The container entrypoint runs prisma migrate deploy before the server listens.
  • One attack surface. Two ports open on the firewall, and the database on neither.
  • Front ends are disposable. Vercel can rebuild them from git at any time; nothing is lost.
  • Deploys are independent. Backend goes via GitHub Actions; front ends via Vercel's own git integration.
  • Rollback is an image tag. The three most recent backend images are kept on the box.
02

The organising idea

How a Mistake Announces Itself Both

Every failure in this stack falls into one of two classes, and the class matters far more than the severity. A loud failure stops you with a message. A silent failure lets you carry on believing it worked.

Ranking these problems by how bad they are is the wrong instinct — it puts "the container will not start" at the top, when that one is harmless because you cannot possibly ship it. The dangerous list is short, and every entry on it looks like success.

Loud — the harmless ones

A message, an exit code, a red run. You cannot deploy them by accident.

  • Port already allocated on docker compose up
  • Environment validation failed, naming every bad variable
  • caddy validate rejecting a duplicate hostname
  • nginx -t reporting a conflicting server name
  • PM2 refusing a duplicate app name
  • A build killed for running out of memory
  • Permission denied (publickey)
VS

Silent — the expensive ones

Everything starts. Everything reports healthy. You find out from the data, later.

  • Compose project name collides → the demo seeds over live bookings
  • Two instances share one Redis → the demo sends real customer email
  • Same-apex session cookies → intermittent logouts on both sites
  • REVALIDATE_SECRET mismatch → the public site serves stale prices forever
  • Tunnel on the wrong port → you edit production thinking it is the demo
  • NEXT_PUBLIC_ENABLE_TRACKING left on → test bookings in real ad data
  • A bare port instead of 127.0.0.1: → the database is on the internet
The colour red in this document never means "serious". It means nothing will tell you. Those are the paragraphs to read twice.

Why the silent list is silent

Three structural reasons, and knowing them lets you predict the next one rather than memorising a list.

CAUSE 01
Both outcomes are valid states

A Postgres volume is a Postgres volume. Compose cannot know that attaching to that one is a catastrophe and this one is correct. Nothing is malformed, so nothing errors.

CAUSE 02
The check happens somewhere else

A revalidation secret is verified by the receiving app, which answers 401 into a log you are not reading. The sending side considers its job done.

CAUSE 03
Build-time values freeze

Anything NEXT_PUBLIC_* is compiled into the bundle. Fixing the variable and restarting changes nothing at all — only a rebuild does — so the fix appears not to work.

The three verifications that catch what nothing else does

Most of the smoke test in §16 is confirming that loud things did not happen. These three are different: each one is the only way to detect a specific silent failure.

The checks that look redundant and are not

Verification 01 · catches a shared database volume Create a booking on the demo, then count bookings in production The count must be unchanged. If the two stacks share postgres-data, both containers are healthy, both sites work, and the demo is writing into live data.
Verification 02 · catches a cookie collision Sign into the demo, then reload production in the same browser You must still be signed in there. The cookie is named identically on every instance; only its Domain separates them, so a shared apex means each login quietly evicts the other.
Verification 03 · catches a publicly bound port From your laptop, curl the API's raw port on the VPS IP It must time out. A response means Docker bound 0.0.0.0, and Docker writes iptables rules ahead of UFW, so the firewall you configured is not involved.

curl --max-time 5 http://YOUR_VPS_IP:5150/api/v1/health
# expected: curl: (28) Operation timed out
# a 200 here means the API is on the public internet with no TLS

The Redis conflict has no config-level fix

buildRedisConnection() in backend/src/common/utils/redis.util.ts sets host, port and password — there is no db index and no BullMQ prefix. Queue names are hardcoded constants shared by every instance: platform-jobs, media-upload, and the content-translation queue. Two instances pointed at one Redis therefore share a keyspace and a queue, and each one's workers will consume the other's jobs — the demo picking up a production job means a real confirmation email sent and a real conversion fired, processed against demo data.

The compose stack gives each instance its own redis container, so this is safe by default. It only bites if you point both at one shared Redis, most likely by reusing a single UPSTASH_REDIS_URL across both env files. Separating them properly would need a code change.

A decision, made once

Caddy or nginx Both

Either works. Only one hostname is proxied on the demo box, so neither choice is much work. But three nginx defaults are wrong for this API, and each one fails in a way that looks like an application bug.

Caddynginx
Config for the demo~6 lines~25 lines across 2 files
TLSAutomatic, renews itself, nothing to schedulecertbot issues; a systemd timer renews
Forwarded headersDefaultYou must set them
Request bufferingStreams by defaultYou must turn it off
Body size limitNoneDefaults to 1 MB
If renewal breaksRetries and logsYou find out when the certificate expires
FamiliarityFewer people know itAlmost everyone; more answers online

The three sharp edges, precisely

EDGE 01 · HEADERS
Rate limiting collapses

Without X-Forwarded-For, the backend's per-IP limiter counts every visitor as one client, so a single busy user throttles everybody. Better Auth also builds http:// callback URLs.

The app trusts exactly one hop — trust proxy 1 in backend/src/main.ts.

EDGE 02 · BUFFERING
Every Stripe webhook fails

Signature verification reads the raw bytes — the backend bootstraps with rawBody: true. Buffering rewrites the body, so validation fails and payments silently never confirm.

EDGE 03 · BODY SIZE
Uploads die at 1 MB

nginx answers 413 above its default, so media uploads fail at a threshold nothing in the application explains or logs.

How to choose

Caddy gets all three right with no configuration, which is why the runbooks lead with it. Choose nginx if you already run it on this box for something else — you cannot run both, they each want port 80 and whichever starts second fails — or you need an nginx-only feature, or you simply want config you can read at a glance. It is a perfectly good choice with three edges you now know about.

Standing it up · step 1

Domains and the Cookie Both

This is the decision that is most painful to change later and the one that fails least visibly. Get the shape of the hostnames right before you buy a certificate for any of them.

The session cookie is named identically on every instance. cookiePrefix is not configured in backend/src/auth/auth.instance.ts, so every deployment uses Better Auth's default, better-auth.session_token. Only the cookie's Domain attribute separates them — and Domain matching includes subdomains at any depth.

Rule 1 — the demo goes on a different apex

Two apexes cannot reach each other · one apex leaks in both directions

If you ever genuinely need the demo under the production apex, make the prefix env-driven rather than working around it:

backend/src/auth/auth.instance.ts
advanced: {
  cookiePrefix: process.env.AUTH_COOKIE_PREFIX ?? 'better-auth',
  crossSubDomainCookies: { /* unchanged */ },
}

…then set AUTH_COOKIE_PREFIX=demo-auth on the demo only. A separate apex avoids needing it at all.

Rule 2 — make demo the parent label, not a child one

COOKIE_DOMAIN must be the smallest domain covering all your hosts. Where you put the word demo decides what that domain is:

LayoutSmallest covering domainVerdict
api.demo.tripwheel.io, app.demo.…, dashboard.demo.….demo.tripwheel.ioScoped to the demo instance
demo.api.tripwheel.io, demo.app.…, demo.dashboard.….tripwheel.ioLeaks to every subdomain of the company domain

tripwheel.io is the company domain. A session cookie scoped to .tripwheel.io is sent to every unrelated service on it. backend/.env.production.example warns about exactly this: scope it to the smallest domain covering both the front end and back end hosts, not a broader shared apex.

Cloudflare

Keep the proxy off — grey cloud — for the API hostname. The orange cloud adds a second proxy hop and the backend trusts exactly one (trust proxy 1), so rate limiting would count Cloudflare's IP as every visitor. Left at 1 behind two hops, clients can also spoof X-Forwarded-For to evade the per-IP limit or poison a victim's bucket.

Email DNS — silent until you look

Add your domain in Resend and paste its DKIM / SPF / DMARC records into the same zone. Until it shows "verified", every booking confirmation, password reset and operator invite silently fails to send. Nothing in the application errors.

Standing it up · step 3

Preparing the VPS Both

Ubuntu 24.04. The demo needs 2 GB of RAM because the Next builds happen on Vercel; production needs at least 4 GB plus swap, and two instances on one box want 8 GB.

a · A deploy user

# ssh root@YOUR_VPS_IP
apt update && apt upgrade -y
adduser deploy
usermod -aG sudo deploy
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy/

Open a second terminal and confirm ssh deploy@YOUR_VPS_IP works before locking root out. If you skip this and the key copy failed, you have locked yourself out of your own server.

sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh
What this means later

PasswordAuthentication no means the deploy password can never log you in over SSH. It exists for sudo and nothing else. If you forget it, you are not locked out — see §33. And PermitRootLogin no constrains sshd only; your host's browser console is not SSH, so root still works there.

b · Firewall — three ports, and the database on none of them

ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable

c · Swap

Small, but it stops the Docker build being OOM-killed. Use 2 GB for the demo, 4 GB where Next builds run on the box.

fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

d · Docker

curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy
# log out and back in as deploy, then:
docker ps          # must work without sudo

e · Node, pnpm, PM2 Prod only

The demo needs none of this — the API ships inside its image and the two Next apps build on Vercel. Install it only where front ends run on the box.

curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
sudo corepack enable && corepack prepare pnpm@10 --activate
sudo npm install -g pm2

f · Log rotation, before the disk fills

Docker's json-file driver keeps container logs forever by default. A full disk takes down Postgres in a way that reads like corruption.

/etc/docker/daemon.json
{ "log-driver": "json-file", "log-opts": { "max-size": "20m", "max-file": "5" } }
sudo systemctl restart docker

Standing it up · step 4

Code onto the Server Both

There are two SSH key pairs in this deployment, they point in opposite directions, and confusing them produces a publickey error that looks the same either way.

Two key pairs, two directions

KEY PAIR 01 · GENERATED ON THE VPS
VPS reads GitHub

A deploy key on the repository, so the server can clone and pull a private repo. Public half goes to GitHub → repo → Settings → Deploy keys. Leave Allow write access unchecked — the VPS only ever reads.

KEY PAIR 02 · GENERATED ON YOUR LAPTOP
GitHub Actions writes to the VPS

Public half appended to deploy@'s authorized_keys; private half pasted into the VPS_SSH_KEY repository secret. This is §15.

Key pair 1 and the clone

# as deploy, on the VPS
ssh-keygen -t ed25519 -C "demo-vps-readonly" -f ~/.ssh/id_ed25519 -N ""
cat ~/.ssh/id_ed25519.pub        # paste this into GitHub as a deploy key

ssh -T git@github.com            # should greet you by name

sudo mkdir -p /opt/demo-tripwheel && sudo chown deploy:deploy /opt/demo-tripwheel
git clone -b main git@github.com:pixeldevripon/demo.tripwheel.git /opt/demo-tripwheel

The layout that the deploy workflow depends on

One clone, not three. The git root and the compose directory are different folders, and that distinction is load-bearing:

/opt/demo-tripwheel/            <- git root. This is VPS_APP_DIR.
├── .github/workflows/             GitHub reads these nowhere else
├── backend-frontend/           <- docker-compose.yml lives HERE
│   ├── backend/                   the only thing the VPS runs
│   └── frontend/                  built by Vercel, not here
└── dashboard/                     built by Vercel, not here
Why the split matters

The deploy workflow runs git reset --hard <sha> in VPS_APP_DIR and then cds into backend-frontend/. Point VPS_APP_DIR at the compose directory and the git step fails with not a git repository.

The same git reset --hard is why any hand edit to a tracked file on the server is temporary. It survives until the next backend deploy and then silently reverts. If you need a change on the box — a published port, a compose tweak — commit it to the repository instead.

Production — three clones Prod

cd /srv/tripwheel

git clone -b prod git@github.com:pixeldevripon/island-tours.git island-tour-development
git clone -b main git@github.com:pixeldevripon/dashbaord-tripwheel-x-islandtours.git tripwheel-x-islandtours-dashboard
git clone -b main git@github.com:pixeldevripon/tripwheel.app.git tripwheel-app

The typo in dashbaord-… is the real repository name. Note that the branches differ: prod for the API workspace, main for the other two.

Secrets Both

Generate a complete fresh set per instance, once, and keep the output. Never copy production's values into a demo — most of all ENCRYPTION_KEY, which decrypts the Stripe keys and operator tokens held in the database.

echo "POSTGRES_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')"
echo "REDIS_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')"
echo "BETTER_AUTH_SECRET=$(openssl rand -base64 32)"
echo "TRAVELER_SESSION_SECRET=$(openssl rand -base64 32)"
echo "INTERNAL_API_SECRET=$(openssl rand -base64 32)"
echo "REVALIDATE_SECRET=$(openssl rand -base64 32)"
echo "ENCRYPTION_KEY=$(openssl rand -hex 32)"
echo "ADMIN_PASSWORD=$(openssl rand -base64 18)"
# production also wants:
echo "SYSTEM_ADMIN_PASSWORD=$(openssl rand -base64 18)"
SecretJobIf it is wrong
INTERNAL_API_SECRETLets the Next servers skip the API's per-IP rate limit while renderingBuilds hit 429 mid-render; logged-in users get bounced
REVALIDATE_SECRETLets backend and dashboard clear the public site's page cachePublic site serves stale prices. No error anywhere

Matched pairs

INTERNAL_API_SECRET and REVALIDATE_SECRET must match within an instance — the API and both of its front ends — and must differ between instances. Both are server-only and must never carry a NEXT_PUBLIC_ prefix, which would publish them in the browser bundle.

The backend validates its environment at boot and prints exactly what is wrong. In production it hard-fails without INTERNAL_API_SECRET. Secrets under 32 characters are rejected, and anything containing change-me is rejected as a placeholder. This is one of the loud failures — you cannot ship a missing secret.

Standing it up · step 7

First Boot Both

cd /opt/demo-tripwheel/backend-frontend
docker compose up -d --build       # first build: 10–20 min
docker compose logs -f backend

The entrypoint runs migrations before the server listens, so a healthy first boot prints these three lines in this order:

[entrypoint] Applying database migrations (prisma migrate deploy)...
[entrypoint] RUN_SEED=true -> seeding database (prisma db seed)...
[entrypoint] Starting server -> node dist/src/main.js

Then turn the seed off — immediately

sed -i 's/^RUN_SEED=true/RUN_SEED=false/' .env
docker compose up -d
curl -s http://127.0.0.1:5150/api/v1/health

Left at true, every redeploy re-seeds. On a demo that is not destructive but it will silently reset content you were part-way through showing someone. Optional demo content afterwards: docker compose exec backend pnpm prisma:seed:demo.

Health checks — what they do and do not prove

Compose health-checks all three services. The backend's check uses node -e with global fetch rather than curl, because the runtime image is node:24-slim and has no curl. Its start_period: 60s matters: migrations run before the server listens, and without it a slow migration looks like a failing container.

The endpoint itself is shallow — it returns { status, timestamp, uptime } and does not check Postgres or Redis liveness. An uptime monitor pointed at it tells you the process is up, not that the database is reachable. Deepening it with @nestjs/terminus is a small future task.

Standing it up · step 8a

The Access Model Both

Postgres publishes exactly one port, bound to the VPS loopback. Nothing on the internet can reach it, and an SSH tunnel is the only way in. You do not have to give that up to get a table browser.

backend-frontend/docker-compose.yml → postgres service
  postgres:
    ports:
      # LOOPBACK ONLY. 5433 because production holds 5432 on this box.
      - '127.0.0.1:5433:5432'

Three numbers, three machines

This is the thing that confuses everyone once, and the confusion is reasonable: there are three different ports in the chain and each belongs to a different computer.

One connection, three translations

Your machine VPS host Container

The SSH hop is the only part that crosses the internet, and it is the only part that is encrypted — which is why the client's SSL setting must be off.

Why 5434 and not 5433 on the Mac

Four different Postgres endpoints can be in play on one laptop. They are deliberately on different numbers so a misconfigured client fails to connect instead of quietly editing the wrong database.

VPS loopbackYour tunnel's local port
Demo54335434
Production54325433
Local dev compose—5432, published directly, no tunnel
Postgres installed on your Mac—5432
The risk is not a crash. It is that 5433 meaning "production" in one terminal and "demo" in another connects your GUI to whichever you started last — with no error, and no visible difference until you change something.

One number per environment, permanently. On your Mac, 5434 is always the demo.

The tunnel

ssh -N -L 5434:127.0.0.1:5433 deploy@YOUR_VPS_IP

-N means "no remote command, just forward". It prints nothing and does not return — that is success. Any output at all is a problem. Close it with Ctrl+C when you are done, and open a separate terminal tab for everything else.

OutputMeaning
nothing, cursor sits thereWorking
bind: Address already in useA tunnel is already on 5434
Permission denied (publickey)Wrong key — see below
Could not resolve hostname deploy:1.2.3.4A colon instead of @
If it fails with Permission denied (publickey), it is your key, not your password

The VPS sets PasswordAuthentication no, so a password cannot log you in even when you remember it. What the message means is that none of the keys your client offered was accepted — and SSH only offers ~/.ssh/id_rsa, id_ecdsa and id_ed25519 by default. A key saved under any other name is never sent.

A Host block does not rescue you. It matches on the alias you type, not the address it resolves to — so a block carrying the right IdentityFile is ignored the moment you connect as deploy@1.2.3.4 in full. Either use the alias, or pass -i ~/.ssh/<key>. Confirm what SSH will really offer with ssh -G <target> | grep -i identityfile.

Make it one word

~/.ssh/config
Host demo-db
  HostName YOUR_VPS_IP
  User deploy
  IdentityFile ~/.ssh/laptop-to-vps
  IdentitiesOnly yes
  LocalForward 5434 127.0.0.1:5433
  ServerAliveInterval 30
  ServerAliveCountMax 3
  ExitOnForwardFailure yes

Then it is just ssh -N demo-db, or ssh -fN demo-db to background it and get your prompt back. IdentityFile is the line that matters; IdentitiesOnly yes stops SSH offering every other key first, which on a machine with several can exhaust the server's MaxAuthTries before the right one is reached. ExitOnForwardFailure makes a port clash refuse loudly instead of connecting with a dead forward.

pgAdmin 4 Both

pgAdmin has two modes, and which one you are in decides how much work everything else is. Choose deliberately, because "I want it in a browser" is a bigger commitment than it sounds.

Desktop mode — what you get by default

The same web application, rendered in an Electron window instead of a browser tab.

  • Zero setup — install and open
  • No login account
  • No master password
  • DATA_DIR defaults to ~/.pgadmin, which works
VS

Server mode — what "in a browser" means

A multi-user deployment mode. Everything it drags in is there to serve a team, not you.

  • A pgAdmin login account you must create
  • A master password encrypting saved server passwords
  • DATA_DIR defaults to /var/lib/pgadmin, absent on macOS
  • A config file, and a port that collides with the dev API
The simple approach, stated plainly

Use the desktop app. It is the identical UI — same React application, same server underneath — and it needs nothing configured. Reach for a real browser only when you actually need a browser: a shareable tab, an extension, or access from another device. That requirement is rarer than the instinct to have one.

There is no shortcut into the desktop app's own server

The obvious idea is to skip server mode entirely: the desktop app is a web server, so find its port and open that in Chrome. It does not work, and it is deliberate.

# the desktop app's own listener, a fresh random port every launch
lsof -nP -iTCP -sTCP:LISTEN | grep -i python
# Python  16631  TCP 127.0.0.1:50906 (LISTEN)

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:50906/
# 401

Desktop mode guards its server with a per-launch token that only the Electron shell holds, so a browser gets 401 Unauthorized. The port changes every time you start the app, and so does the token. That is why the browser route means running a second instance in server mode rather than borrowing the first.

Connecting, in either mode

Register → Server:

  • General tab: a name you will recognise, e.g. demo.tripwheel.
  • Connection tab: host 127.0.0.1, port 5434, database island_tours, user island, password from §17. Leave SSL mode at prefer — it falls back cleanly, unlike require.
  • Leave the SSH Tunnel tab off and keep ssh -N demo-db open.

To let pgAdmin build the tunnel instead: SSH Tunnel tab → Use SSH tunneling, tunnel host YOUR_VPS_IP, port 22, username deploy, Authentication → Identity file, Keep alive 60. Then change the Connection port to 5433, because it is now resolved on the VPS. If the switch is greyed out, SUPPORT_SSH_TUNNEL is off in your config; it is on by default in both modes.

The Identity file field is where this fails, and the dialog will not tell you

pgAdmin's file picker hides dotfiles, so ~/.ssh is not browsable and the field is easy to leave empty — and it does not expand ~ either. Type the absolute path: /Users/devripon/.ssh/laptop-to-vps. Left empty, pgAdmin falls back to password authentication, which a keys-only VPS refuses, and the dialog shows a generic failure.

What lands in ~/.pgadmin/pgadmin4.log is Could not establish session to SSH gateway. That is the SSH leg failing before Postgres is reached — so nothing on the Connection tab is at fault and changing the port will not help. Read that log first.

To prove the key itself is innocent, test with pgAdmin's own bundled paramiko rather than with ssh. Paramiko is what the tunnel actually runs on, and it is a different implementation with different defaults:

"/Applications/pgAdmin 4.app/Contents/Frameworks/Python.framework/Versions/3.13/bin/python3.13" - <<'PY'

c = paramiko.SSHClient()
c.set_missing_host_key_policy(paramiko.AutoAddPolicy())

          allow_agent=False, look_for_keys=False)

SSH AUTH OK here with a failure in the dialog means the form is wrong, not the key. If you cannot make the form behave, the manual tunnel on 5434 costs one terminal and always works.

In a browser — run pgAdmin on the VPS, in the compose stack

This is the recommended browser route, and it is recommended because it deletes the hard part rather than working around it. pgAdmin running inside the stack sits on island-net alongside Postgres and reaches postgres:5432 container to container. No tunnel between pgAdmin and the database means no 5433 versus 5434, no Identity file field, no paramiko, and no SSH leg to debug. The only tunnel left forwards pgAdmin's own HTTP port to your laptop.

Where the SSH hop moves to

CLIENT ON YOUR MAC
Two hops, both yours to configure

SSH from the Mac to the VPS, then Docker's port forward to the container. The client has to be told about both, in different units, and the SSH leg is the one that fails opaquely.

PGADMIN ON THE VPS
One hop, and it is not a database hop

SSH forwards pgAdmin's web port. pgAdmin to Postgres is a service name on a private network — nothing to configure, nothing to translate, nothing to get wrong.

The service is already in docker-compose.yml, behind a profile:

  pgadmin:

      - '127.0.0.1:8082:80'      # loopback only, same rule as postgres
    networks:
      - island-net

deploy-backend.yml runs a plain docker compose up -d, and compose skips profiled services entirely. So pgAdmin never starts itself on a deploy, never costs the demo box its ~200 MB, and is never left running unattended. Verified: docker compose config --services lists three services; adding --profile tools lists four.

THE SECURITY BOUNDARY
The 127.0.0.1: prefix

A bare '8082:80' puts a pgAdmin login on the public internet, and Docker's iptables rules mean UFW will not stop it. pgAdmin is a large attack surface; loopback plus SSH is what makes running it acceptable at all.

STILL SERVER MODE
But the container does the work

There is a login account, created for you from the environment. None of the setup-db, DATA_DIR or bundled-Python work that a local server-mode install needs applies here.

STATE
pgadmin-data

Persists the registered server and your preferences. Without the volume you would redo both on every restart.

Do not put it on a subdomain

The local routes, and why they are no longer worth it

PGADMIN IN SERVER MODE ON YOUR MAC
Works, but you build it yourself

Either pip install pgadmin4 — which on macOS first needs a Homebrew Python and a venv, because the system Python is 3.9 from the Xcode command line tools — or running the desktop app's bundled Python in server mode, which avoids the install but needs a config_distro.py overriding DATA_DIR (server mode defaults it to /var/lib/pgadmin, absent on a Mac), a launcher script, a setup.py setup-db run and a master password.

Both arrive where the compose service starts.

A DOCKER RUN ON YOUR MAC
Cannot work at all

Inside the container 127.0.0.1 is the container, and ssh -L binds only 127.0.0.1 and [::1] on the host — so host.docker.internal is refused. Making it reachable means ssh -L 0.0.0.0:5434:…, publishing the demo database to your whole LAN.

Isolation and Sizing Both

How Docker isolates the two stacks

There is no container_name in docker-compose.yml, and the volumes and network are named relatively — postgres-data, redis-data, island-net. Compose prefixes all three with the project name, which defaults to the directory name:

/opt/island-tours/opt/demo-tripwheel
Volumeisland-tours_postgres-datademo-tripwheel_postgres-data
Networkisland-tours_island-netdemo-tripwheel_island-net
Containerisland-tours-backend-1demo-tripwheel-backend-1

So the two databases are already separate, and the two Redis instances too. Pin the name explicitly anyway — one line in each .env. That isolation currently rests on nothing but the directory being named what you expect.

# /opt/island-tours/.env
COMPOSE_PROJECT_NAME=island-tours

# /opt/demo-tripwheel/backend-frontend/.env
COMPOSE_PROJECT_NAME=demo-tripwheel

Adding the line to production's file changes nothing about the running stack until its next docker compose up, and the name it resolves to is identical — so the value is declared on both sides rather than inferred on both sides.

Sizing — the real constraint

Two full instances means 2 Postgres + 2 Redis + 2 NestJS APIs, plus up to six Next.js servers if both run their front ends on the box. One stack wants 4 GB; two want 8 GB, and the Next builds are the spike rather than steady state.

01
Build one app at a time

Never in parallel across instances. Six production builds racing for memory is how you get an OOM kill with no useful error.

02
Ask whether the demo needs everything

A demo that is just the public site plus the dashboard drops a third of the footprint and two hostnames. On this repo that is already the case — Vercel builds them.

03
Lower max_memory_restart on the demo

So that under memory pressure the demo restarts first and production stays up.

Day-to-day, with two stacks this similar

Every docker compose command acts on whichever project you are standing in, which is a real footgun.

# always cd first. `docker compose down` in the wrong directory stops production.
cd /opt/demo-tripwheel/backend-frontend && docker compose ps
cd /opt/island-tours && docker compose ps

# PM2 is name-scoped, so it is safer:
pm2 restart demo-public
pm2 logs demo-dashboard --lines 100

A habit worth forming: set the shell prompt, or use two clearly labelled terminal tabs. The single most likely accident here is a destructive command in the right shell and the wrong directory.

Reload, not restart — zero downtime, and a bad config leaves the old one running.

Two redeploy traps

A NEXT_PUBLIC_* change does nothing until a rebuild. It is compiled into the bundle at build time, so restarting the process changes nothing and the fix looks broken.

A hand edit on the VPS is reverted by the next backend deploy. git reset --hard runs before every build. Nothing logs it — the file simply goes back, and whatever depended on it stops working.

Watch disk, not just memory

Docker layers accumulate on every --build, and VPS disks are small. A full disk takes down Postgres in a way that reads like corruption.

df -h
docker system prune -af --filter "until=168h"
Not --volumes. Ever.

That flag deletes postgres-data. The reclaim step in the deploy workflow is deliberately scoped to images and build cache for the same reason.

The Postgres password is baked into the data volume the first time the container initialises. Changing the environment variable alone does not change an existing database's password.

Postgres — password only, keep data

# 1. change it inside the running database

docker compose down

# edit .env: REDIS_PASSWORD=NEW_REDIS_PASSWORD

Three things that make it work

BYPASS
Trusted internal origin

skipIf: isTrustedInternalOrigin — the SSR and build servers send x-internal-api-key matching INTERNAL_API_SECRET, so prerender bursts are not throttled. Everyone else is limited.

That secret is required in production; the validator refuses to boot without it.

REAL CLIENT IP
trust proxy = 1

main.ts trusts exactly one hop, and the proxy forwards X-Real-IP / X-Forwarded-For, so the limiter sees the visitor rather than the proxy.

SEPARATE LAYER
Auth brute force

Handled by Better Auth's own per-path limiter — rateLimit.customRules, 5/min on sign-in, forget and reset. /api/auth/* is @SkipThrottle()'d from the NestJS guard, so login limits are governed solely there, and the internal-key bypass does not touch it.

The tripwire in trust proxy = 1

It assumes exactly one proxy hop. Put a CDN or load balancer in front of your proxy — Cloudflare's orange cloud, another LB — and it becomes two. Left at 1, clients can spoof X-Forwarded-For to evade the per-IP limit or poison a victim's bucket. Bump it to 2 in main.ts, or use nginx real_ip with the CDN's header.

Tuning

  • Global: edit the throttlers array in auth.module.ts.
  • Per route: @Throttle({ short: { limit: 5, ttl: 60_000 } }) on a controller or route — use this to tighten register and reset-password.
  • Skip: @SkipThrottle(), already on /health and Stripe webhooks.

The default store keeps counters in memory — correct for one container. With multiple replicas each has its own counter, so the effective limit multiplies by the replica count. Sharing them means swapping in a Redis-backed throttler storage pointed at your existing Redis. That becomes relevant only alongside §30.

Scaling Both

Honest framing: a single VPS does not auto-scale the way a cloud platform does. The realistic options, cheapest first.

Three tiers, in the order you should reach for them

Tier 1 · you are here Vertical — resize the VPS More vCPU and RAM in the Hostinger panel. Zero code change, one reboot. Do this first; one well-sized VPS carries this workload a long way.
Tier 2 · manual, not automatic Horizontal on the same box Multiple backend containers behind the proxy. Requires moving rate-limit state to Redis, and making sure the nightly @nestjs/schedule jobs do not double-run — a Redis lock, or schedulers in exactly one instance.
Tier 3 · a platform change Real autoscaling Docker Swarm is closest to the current compose. k3s adds a Horizontal Pod Autoscaler and a large operational step up. Managed container hosts — Railway, Render, Fly.io, Cloud Run, ECS — give request-based autoscaling with almost no ops.

The application is already stateless — sessions are cookie and database backed via Better Auth, with no in-memory session store — so replicas are safe apart from the two points in Tier 2.

Two things to do before buying a bigger server

FIRST
Push image resizing to Cloudinary

Next's image optimizer is the first thing to saturate CPU on a self-hosted storefront, and the images already live in Cloudinary — which resizes on delivery, free, at the edge. A custom loader emitting .../w_800,q_auto,f_auto/... URLs moves that work off your server entirely.

Only relevant where front ends run on the VPS. Prod

SECOND
Split the front ends off before the backend

If one box stops being enough, move the Next apps elsewhere and leave API + Postgres + Redis together. The apps are stateless and trivially relocatable; the database is neither. Only the proxy's reverse_proxy targets change — CORS_ORIGINS stays exactly as it is, because it lists public origins, not machines.

If you only ever do three things from this manual

Off-site backups you have actually restored once (§27), a working uptime monitor (§28), and the three silent-failure verifications (§16). Those turn "the site is down and I do not know why or for how long" into a solved problem. Everything else is optimisation.
