    Island Tours Review System, Build vs Buy

    Companion to the review strategy advisory. June 18, 2026. Question answered: are there existing review systems Island Tours can buy, or open-source code it can reuse, instead of building from scratch? Method: four-angle deep research (commercial review SaaS, travel and tours specific systems, open source and self-hostable code, and a build-vs-buy fit analysis), with current 2026 primary sources (vendor developer docs and pricing pages, Google Search Central, EUR-Lex, OTA help centers, GitHub).

    This document contains zero em-dashes, per the working agreement.

    Bottom line

    There is no off-the-shelf review system that fits Island Tours well, and there is no mature open-source one you can drop in either. The honest answer to "is this for sale or findable as code" is: the pieces are, the system is not.

    • For sale: plenty of review SaaS exists, but almost all of it is built for Shopify e-commerce or for hotels. The few that expose a true headless API can technically take your verified-booking signal, but none does tour-plus-operator attribution natively, none gives you organic rating stars on your own pages (Google's self-serving rule blocks widget reviews), most price per booking (the wrong cost curve for a marketplace), and some keep a license on your review content after you leave.
    • As code: there is no production-grade standalone open-source review system for a Next.js and Supabase stack. What exists is either welded to a whole commerce platform (Medusa, Sylius, Shopware) or a single-digit-star solo project. The realistic path is to build a thin, owned module using two MIT reference implementations for the data model and a set of genuinely mature building blocks for moderation and translation.
    • The structural reason buying loses: your hard requirement is reviews gated on Island Tours' own confirmed bookings, attributed to both tour and operator, on your own domain. Verified-booking gating is only possible if the review system can read your booking graph. A third-party widget structurally cannot. This is exactly why every comparable marketplace (Viator, GetYourGuide, Booking, Airbnb, Etsy) builds first-party.

    Recommendation: build first-party on your existing stack, own the data in an EU-region database, render the reviews server-side into island.tours. If you need to launch faster than engineering allows, the only acceptable shortcut is a headless, own-the-data collection vendor rendered server-side and synced into your own database, never a drop-in widget. The conditions under which buying actually wins are narrow and listed at the end.

    This corroborates the build-first-party direction already in the review strategy advisory. The new finding is how decisively the market confirms it.

    Part 1. What is for sale: commercial review SaaS

    The large review platforms split into three groups by how well they fit a custom (non-Shopify) tours marketplace that needs to submit verified-booking reviews by API and display them on its own domain.

    1.1 The few with a real headless API

    These can ingest your own booking signal and return review data as JSON for you to render server-side. They are the only buyable options worth considering for a custom build.

    Platform Headless fit Verified-booking by API SEO and data ownership Pricing signal
    REVIEWS.io Best mechanical fit. Documents the whole loop: read reviews as JSON, fire order-id-keyed invitations, and directly insert a pre-collected review carrying your own order_id and photos. Native machine translation (matters for 7 locales). Google Licensed Review Partner. branch maps to operator, sku to tour. Yes, direct insert with your order id. Stars can reach Google store ratings. Ownership caveat: their terms keep a perpetual license to review content after cancellation. API gated to the paid "Plus" or "Grow" plan; third-party estimates roughly 299 to 499 USD per month per domain. Treat exact price as an estimate.
    Yotpo Works headlessly: read reviews.json plus a Core Orders feed that auto-tags Verified Buyer when an email matches a past order. No Shopify required. Yes, but verified-buyer at creation needs a sales-gated HMAC, and multilingual off Shopify needs a separate domain and app key per locale (a real gotcha at 7 locales).     PowerReviews Genuinely API-first and platform-agnostic: separate Read and Write APIs, the Write body includes order_id, reviewer_type, source. Yes, driven by feeding your own order feed.     The recommendation inside this group: if you buy a collection layer to accelerate, Yotpo or Stamped grant the cleanest ownership of your review content, which matters more than raw mechanics for a system you may later bring fully in-house. REVIEWS.io is the best mechanical match (its order-id insert plus invitation plus JSON read mirror exactly what an in-house verified-booking system does), but weigh its perpetual post-cancellation content license. Avoid Bazaarvoice on weight and ownership for a single domain.

    1.2 Strong collection, poor headless display

    • Feefo is the best conceptual match for verified bookings and is travel-native, with a first-class operator-versus-tour review split and multi-stage after-booking journeys. But its own docs say the Reviews API is not suitable if you plan to self-host the data, the only bulk export is deprecated, and you can never post a review yourself (only the invited customer via Feefo's form). Sanctioned display is Feefo-hosted widgets. Good model, wrong architecture for an SEO-owning SSR build. List pricing around 149 to 299 GBP per month per domain.
    • Trustpilot Product Reviews can invite by your booking reference and attach photos, but there is no direct review insertion, the company-review SEO value lives on trustpilot.com, and the API is enterprise-gated. Use Trustpilot for the platform-trust layer (as the strategy advisory already recommends), not for tour reviews.

    1.3 Shopify-bound or wrong shape, eliminate

    • Okendo: "headless" means headless Shopify; review ids are Shopify product ids; no create-review API. Poor fit.
    • Judge.me: sunsetting all non-Shopify platforms through January 2026; API requires a live myshopify.com domain; API-created reviews cannot be verified or order-linked. Impossible.
    • Loox: Shopify-exclusive end to end; its 2026 API is read-only. Hard fail.
    • Junip: effectively Shopify-only; display API read-only and premium-gated; no submit by API. Poor fit.
    • Stamped: the one Shopify-cluster vendor with a documented custom-platform path and clean data ownership, verified-buyer keyed off order data you push, but Shopify-first in posture and no native machine translation. A marginal headless option, behind REVIEWS.io and Yotpo.
    • Trustmary: testimonials and Google-review aggregation, widget-centric, no booking-gated tour-level reviews. Out of scope.

    1.4 The cross-cutting reality

    Every vendor's turnkey rich-snippet and rating-star tooling is built for its own JavaScript widget. In a real Next.js server-rendered build you write the schema.org JSON-LD yourself from the JSON API regardless of which vendor you pick. So the "SEO out of the box" selling point does not apply to your architecture, which removes a big part of the reason to buy.

    Part 2. Travel and tours specific systems, and third-party review sources

    This is the group you might expect to fit, being in the same industry. It does not.

    2.1 Hospitality review platforms serve hotels, not a reselling marketplace

    TrustYou, Revinate, Customer Alliance, GuestRevu, and Reputize are hotel reputation tools. They assume a property and room-night model, verify against a stay rather than your transaction, display an aggregated score rather than dual-attributed reviews, have no path to ingest a Supabase booking feed, and several are priced per room or per property, a unit that does not exist for a tours OTA. Drop all five. The closest affordable, industry-agnostic, embeddable one (Trustmary) is a display layer only and does not verify against your bookings.

    2.2 Tour booking software serves operators, not resellers

    FareHarbor, Rezdy, Bokun, Checkfront, TourCMS, Peek Pro, Ventrata, and TrekkSoft are operator-side reservation systems. The decisive finding, confirmed from their API endpoint references rather than marketing: none exposes review content to a reseller via API. Every review feature is the operator's own reputation funnel to the operator's own Google or Tripadvisor listing. The OCTO open standard that several use for reseller connectivity has no reviews capability at all. Even Bokun, owned by Tripadvisor, locks its Tripadvisor reviews widget to the operator's own listing and gives resellers only rating-based product filtering, not review content to republish. A review locked inside an operator's FareHarbor account does not help Island Tours.

    2.3 Third-party review sources are legally hostile to this use case

    You might hope to display Google, Tripadvisor, or Viator reviews. The licensing makes that impractical for an SEO-owning marketplace.

    Source Reviews you get Store or cache? Search-indexable? Mix with your own reviews?
    Google Places API 5 max, tied to a place No, only the place id No Yes, but ephemeral
    Tripadvisor Content API About 3 per location No No (must be non-indexable) No, a clause forbids displaying alongside any other reviews
    Viator Partner API All reviews per product Yes, under 24h TTL No, must load via blocked JavaScript Tied to Viator's catalogue, and booking redirects to viator.com
    GetYourGuide Partner API None to affiliates n/a n/a n/a

    Two flags. Google and Tripadvisor both forbid storing the review content and forbid indexing it, so they degrade to live, attribution-heavy widgets with no SEO value. Tripadvisor's anti-commingling clause is directly incompatible with showing its reviews next to your own. Viator is the only source that lets you store reviews briefly and show the full set, but it ties you to Viator's catalogue, funnels the booking to a competing channel, and still cannot be indexed. As an EU or Dutch entity you also fall under each provider's EEA-specific terms, several of which are revocable at will. Have a lawyer read any specific order before relying on it.

    2.4 Verdict for Part 2

    There is no off-the-shelf travel or tours review system that fits a custom reselling OTA. The market serves hotels or operators, not a marketplace that resells operators' tours. The only fully owned, indexable, freely mixable, permanently storable, dual-attributable review asset is first-party verified-booking reviews collected on your own bookings.

    Part 3. What is findable as code: open source

    The blunt finding: there is no mature, reusable, standalone open-source review system that drops into a Next.js and Supabase stack and delivers the full spec (verified-booking gating, rating, text, photos, moderation, aggregation, multi-locale, schema.org). That product category effectively does not exist in 2026. Every usable reviews implementation is welded to a host platform, and every truly standalone repo is a single-digit-star solo or beta project. So the realistic path is to build the module yourself, copying the data model and workflow from a couple of permissively licensed references and assembling mature building blocks for the supporting layers.

    3.1 Reference implementations to copy from, not depend on

    These are MIT-licensed and worth reading before you write a line, but you lift patterns from them rather than taking a runtime dependency.

    • Medusa.js product-reviews plugin (Node and TypeScript, Postgres, MIT). The best code reference because it shares your language and database. Lift the table schema, the moderation status enum, and the average-plus-histogram aggregation SQL straight into a Supabase view. Note: the maintained package is the v2 one, not the legacy plugin.
    • Sylius reviews (PHP, MIT). The best architecture reference. Lift the polymorphic "reviewable" pattern (one table can serve both tours and operators), the new to accepted to rejected state machine, and the cached average-rating updater design.
    • Shopware reviews (MIT community edition). Use its feature set as your product-spec checklist: approval gates visibility, owner replies, per-channel and language-scoped display, aggregate plus per-star breakdown.
    • Saleor has no reviews feature at all; Reaction Commerce is discontinued; Vendure's reviews are a GPL-licensed demo plugin. Skip these for reuse.

    3.2 Standalone open-source review projects, all weak

    The honest landscape: the GitHub "rating system" topic is dominated by Elo and TrueSkill matchmaking math, which is irrelevant. Self-hosted comment engines lack stars, verified-booking gating, and aggregation. The few real review repos are all immature: a couple of Medusa review plugins under about a dozen stars each, one NestJS plus Next.js plus Postgres project aimed at marketing testimonials rather than commerce (fork-and-own, high risk), and a feature-complete but officially abandoned VTEX module that only runs inside VTEX. None is production-grade for your use case. The fact that there are several competing Medusa review plugins, none above roughly a dozen stars, is itself the signal: no community standard exists.

    3.3 The realistic starting blocks you would actually use

    • Scaffold: Razikus/supabase-nextjs-template (Apache 2.0, actively maintained, Next.js 15 and Supabase). It already ships auth plus a storage row-level-security file-upload demo, which transfers directly to review photos. The best production-grade base to extend, if you are not just bolting onto the existing app.
    • Rating widget: Kibo UI Rating, a shadcn copy-paste component you own, since shadcn has no built-in rating. Avoid the abandoned star-rating npm libraries.
    • The core logic you write yourself, a few dozen lines each, because no library ships it: a booking-gated insert policy (insert allowed only when a completed booking owned by that user exists for that tour), a unique constraint for one review per booking, per-user-folder storage policies for photos, and a trigger that maintains the denormalized rating average, count, and star distribution on the tour and operator rows.

    3.4 The building blocks that are genuinely production-grade

    This is where mature open source does exist and is worth using:

    • Text profanity (Node): obscenity (MIT, active). Defeats obfuscation, low false positives. Avoid the abandoned bad-words library.
    • Toxicity (optional ML sidecar): Detoxify (Apache 2.0, multilingual), run as a Python sidecar, or the TensorFlow.js toxicity model for a pure-JS English option.
    • Image moderation: NSFWJS (MIT, the default). Run via tfjs-node or a Docker sidecar, route by confidence band to a human queue, and tune the threshold so legitimate beach and tour photos are not rejected.
    • Machine translation: for permissive licensing and self-hosting, OPUS-MT or Helsinki-NLP models on CTranslate2, or LibreTranslate as a separate network service. Google Translate or DeepL give better quality per character at a per-character cost. Reviews are short and high-volume, so a pragmatic hybrid is self-hosted for bulk gist with a paid API for flagged or important text. Avoid NLLB-200, which is non-commercial licensed.

    3.5 Verdict for Part 3

    Fork nothing wholesale. Build a thin, owned reviews module on Supabase, copying the schema and moderation workflow from the Medusa plugin and Sylius (both MIT), using Razikus's template for storage RLS patterns, Kibo UI for the stars, and the obscenity, NSFWJS, and OPUS-MT or LibreTranslate building blocks for the supporting layers. The differentiated work (booking-gated RLS, photo storage RLS, the rating rollup trigger) is a few hundred lines you would write no matter which starting point you chose.

    Part 4. The build-vs-buy decision

    4.1 Why a third-party widget structurally cannot do the core job

    Your hard requirement is reviews gated on Island Tours' own confirmed bookings. That gate is only possible if the review system can read your booking records and confirm a completed, paid booking owned by that customer. A drop-in widget has no access to your booking graph. This is not a configuration gap, it is structural, and it is exactly why every comparable marketplace builds in-house: Viator, GetYourGuide, Booking, Airbnb, and Etsy all gate reviews on their own verified transactions. A SaaS can approximate verification only if you feed it your order data by API, which means you are doing the integration work anyway.

    4.2 The SEO and rich-results trap

    Even if you feed a SaaS your booking signal, you cannot get organic rating stars on your own pages through its widget. Google's review-snippet policy is explicit that when the entity being reviewed controls the reviews about itself, pages using Organization or LocalBusiness structured data are ineligible for star rich results, and this explicitly includes reviews embedded through a third-party widget. The only on-domain route to legitimate review stars is to mark up the review target as the item being reviewed (the tour), not your organization, and to render that markup server-side from your own data.

    Two precisions worth carrying into the build. First, server-side rendering into your own DOM wins on content attribution, indexing speed, and rich-result eligibility all at once; an iframe or JavaScript widget is credited to the vendor's URL and is indexed late or missed. If you ever use a SaaS, you must use it headlessly by API and render server-side, never the drop-in widget. Second, marking a guided tour up as a Product purely to earn stars is a documented gray area: the schema types that best fit an experience (Service, Event, TouristTrip) are not on Google's review-snippet eligible list, so there is some manual-action risk, and Google's late-2025 guidance asks for one clear review target per rating. In practice the whole industry marks experiences up as Products and earns stars, so this is a watch-item to validate, not a blocker, and it slightly tempers the confidence of the schema section in the strategy advisory rather than overturning it.

    4.3 Data residency and GDPR

    Storing EU customers' review text and photos in your own EU-region database is materially cleaner than a US SaaS. The EU-US Data Privacy Framework is in force in mid-2026 but under appeal to the Court of Justice, a live "Schrems three" risk, so a US vendor that is not Framework-certified would need standard contractual clauses plus a transfer impact assessment. Even a US-owned cloud's EU region does not fully escape US jurisdiction under the CLOUD Act. Supabase itself is a US-incorporated company on AWS, so an EU-region Supabase project keeps the data in the EU but the parent still sits under US law; for maximum sovereignty you would self-host Postgres in the EU or hold the encryption keys EEA-side. Review photos are ordinary personal data unless you run facial recognition on them (do not), and you need an Article 28 data processing agreement with any processor, Supabase included. None of this is fatal to using Supabase, but it all points the same way: own the data, host it in the EU.

    4.4 Cost and lock-in at marketplace scale

    SaaS review pricing scales with booking volume, which is the wrong cost curve for a marketplace. The capabilities you actually need (a headless API, multi-language, multiple locales, a custom verified feed, single sign-on) are precisely the enterprise-gated ones, so a SaaS that meets your spec lands you in four to six figures per year and still does not give you booking gating or organic rich results. Annual or multi-year upfront commitments and proprietary exports add an exit tax. Building a reviews feature on an existing Supabase and Next.js stack sits at the low end of custom-software cost and avoids all of that, which is why building becomes the rational steady state once booking volume is meaningful.

    4.5 What this means together

    The four angles converge. The market has no fitting product, the open source has no fitting system, the SEO and verification requirements can only be met first-party, the data should live in your own EU database, and every peer marketplace has reached the same conclusion. Build.

    Part 5. Recommendation

    Build a first-party review system on your existing stack. Own the data in an EU-region Postgres or Supabase database. Render the reviews server-side into island.tours. This is the same conclusion the strategy advisory reached, now stress-tested against the buy and open-source markets and confirmed.

    Concretely, the build is the seven-layer module described in the strategy work: the expanded E.7 schema with booking-gated row-level security and dual tour-and-operator attribution, a tokenized post-tour collection flow, a moderation queue, a nightly-plus-trigger aggregation, server-rendered display with Product-level JSON-LD, machine translation, and the verification disclosure. Copy the data model and moderation workflow from the Medusa plugin and Sylius, and use the obscenity, NSFWJS, and OPUS-MT or LibreTranslate building blocks so you are not writing those from scratch.

    5.1 If you must accelerate: the one acceptable hybrid

    If engineering cannot build this before launch, the only acceptable shortcut is a headless, own-the-data collection vendor, rendered server-side and synced into your own database, never a drop-in widget. Pick a vendor that grants clean ownership of review content (Yotpo or Stamped on those grounds; REVIEWS.io is the best mechanical match but weigh its perpetual post-cancellation license), put it on an EU-region or Framework-certified processor, feed it your booking signal so the verified badge reflects your booking, pull reviews by API, render them first-party, and keep a synced copy in your own EU database so you can graduate to full first-party later without a migration. Use Trustpilot, separately, only for the platform-trust layer as the strategy advisory recommends.

    5.2 The conditions under which buying actually wins

    Buy (headless, owning the data) only if all of these hold at once:

    • You need to launch in weeks, not a quarter, with no engineering capacity for a reviews feature now.
    • Booking volume is low enough that per-order pricing stays inside a small monthly tier.
    • You do not yet need organic rating stars on your tour pages (off-domain reputation is enough short-term).
    • You accept an export and licensing dependency, and you pick an own-the-data vendor on an EU-region or Framework-certified processor.
    • You still render headless server-side and keep a synced copy in your own EU database.

    The moment any one of these breaks (meaningful booking volume, a need for on-site review stars, strict EU residency, or wanting the unique review text as a durable SEO asset) building wins. For a custom verified-booking OTA on Next.js and Supabase, those conditions break almost immediately, so building is the expected steady state.
