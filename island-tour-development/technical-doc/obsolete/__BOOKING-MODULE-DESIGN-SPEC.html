1. Core Principles & Design Invariants

  1. Instant Confirmation, No Enquiries: The booking system operates on a direct seat-sale model. There is no "24-hour operator inquiry" phase; every booking immediately reserves inventory.
  2. Pre-Payment Agentless, Post-Booking Named (Anti-Disintermediation & Anti-Phishing):
    • Pre-Payment: To prevent travelers from booking directly with operators outside the platform, the operator name is hidden or kept generic (e.g., "Local Partner") throughout the search, detail, widget, and checkout stages.
    • Post-Booking: Immediately upon booking (on the Thank-You Page and confirmation email), the operator's actual display name is shown. For operator_link tours, this is a critical security measure (referred to as the C2 Mitigation) to foreshadow that the operator will send a secure balance payment link, ensuring the traveler expects the email and does not flag it as phishing.
  3. Conversion Value is Commission (Not GMV): The value reported to analytics platforms (Google Ads, Meta CAPI, GA4) is the platform's margin (commission_amount in EUR), not the Gross Merchandise Value (booking_total_eur / original_amount). Firing a conversion with a null commission represents data corruption and is blocked.
  4. Guarded Single-Update Booking Claim: Overbooking is prevented via a single conditional SQL UPDATE statement that checks vacancy and increments booked seat counts atomically.
  5. Computed Transient States: Time-based states (booking cutoffs, live status of departures) are computed on-the-fly at read time rather than written to the database.

2. The Four Payment Models

A tour must declare exactly one payment model, which is snapshotted onto the booking at creation as payment_model.

Payment Model Charged at Checkout (Stripe) Balance Handling Created Status Visual / Widget Behavior
operator_link (Default) deposit_pct% deposit Operator emails secure link; balance paid online before deadline. ON_HOLD → CONFIRMED Shows Total, Pay today, Balance later.
on_arrival deposit_pct% deposit Balance paid in person on arrival (card or cash, or cash only, per tour configuration). ON_HOLD → CONFIRMED Shows Total, Pay today, Balance on arrival.
paid_in_full 100% Nothing later — fully paid at checkout. ON_HOLD → CONFIRMED Shows Total and Pay today (zero balance).
operator_full Nothing Operator collects the full amount directly; checkout takes no payment. CONFIRMED at commit Shows Total and Balance later (zero today). CTA is "Reserve my spot".
Zero-Amount Money Rows: To ensure clean UX, any monetary line items representing $0 must be completely hidden (e.g., hiding "Balance later" for paid_in_full, or "Pay today" for operator_full).

4. Unified Cancellation & Free Refund Window

One per-tour window (tour.cancellation_hours) governs both the deadline for balance payments and free cancellations.

  • Allowed Values: Enum [24, 48, 72, 168] hours. Default is 48 hours.
  • Formula: cancelDeadline = tourStartDateTime - cancellation_hours
  • Time Zone: Always calculated and rendered in destination-local time, using the suffix "(local time)".

Cancellation Request Process:

  1. Traveler clicks "Cancel booking" in the email, opening a tokenized page on island.tours: /{destination}/thank-you/{public_ref}.
  2. The page shows: "Cancel {tour}, {date}? Refund ${deposit_amount}" (refund line omitted if nothing was paid).
  3. Submitting the cancellation sends a manual request notification to the admin dashboard.
  4. Deadline Invariant: Refund eligibility is judged on the traveler's request timestamp (utcCancellationRequestedAt), not the admin's action timestamp. Admin processing delays never penalize the traveler.

Anti-Scarcity Mask: Only show exact seat vacancy counts if remaining seats are between 1 and 4 (e.g. "Only 2 left"). If vacancies are 5 or higher, display a generic "Available".

  "booking_currency": "EUR",           // Always EUR normalized

  "tour_id": "tour-uuid-here",
  "tour_name": "Miss Ann Boat Trip",
  "operator_id": "operator-uuid-here",

  "island": "curacao",
  "user_id": "sha256-hashed-email",    
  "user_data": {
    "sha256_email_address": "hashed-email",
    "sha256_phone_number": "hashed-phone-e164",
    "sha256_first_name": "hashed-first-name",
    "sha256_last_name": "hashed-last-name",
    "address": {
      "sha256_city": "hashed-city",
      "sha256_postal_code": "hashed-zip",

Hashing Rule: All PII fields are lowercased, trimmed, and hashed using SHA-256 server-side before being outputted into the HTML layout.

9. Common Edge Cases & Mitigation Strategies

Edge Case Symptom Mitigation
Concurrently Fired Webhooks Stripe confirmation fires twice, creating race conditions. Unique database index constraints on Stripe transaction/event log IDs. Wrapped in strict database isolation locks.
Double Firing of Tracking Pixels Traveler refreshes their Thank-You Page or shares the link, double-counting ads conversion value. The conversion_fired_at column acts as a server-side lock. If populated, the thank-you payload returns conversion: null and tags are skipped.
Timezone Drifts on Deadlines Server UTC checks close booking slots or judge cancellation periods incorrectly. The booking snapshots the local timezone string (tourTimeZone) at creation. All date logic uses localized conversion libraries.
