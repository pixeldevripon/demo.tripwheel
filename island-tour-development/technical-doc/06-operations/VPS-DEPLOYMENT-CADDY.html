Island Tours VPS Runbook

Deploy the whole platform onto one Hostinger VPS: the NestJS API in Docker, the three Next.js apps behind PM2, and Caddy in front handling every domain and certificate automatically. Follow the steps in order — the order matters more than anything else here.

The order you must deploy in

Not a preference — a dependency chain. The Next.js builds call the backend while they prerender pages, so a build against a dead API produces a broken site.

  1. DNS first. Caddy cannot issue a certificate for a name that doesn't resolve to your server.
  2. Backend second. It must be live at https://api.… and answering.
  3. Caddy third, so the API is reachable over HTTPS.
  4. Next.js apps last, because next build fetches from that HTTPS API.
Sizing

Three Next.js production builds are memory-hungry. Give the VPS at least 4 GB RAM and add swap (step 3). On a 2 GB plan the builds get OOM-killed halfway through with no useful error.

01

Pick your domains — once, carefully

This is the decision everything else copies. Get it wrong and you get a login loop that looks like a bug in the code.

All four apps must live under one apex domain. The backend issues the login session cookie scoped to a shared parent domain, so a dashboard on a different apex would sign in successfully and then behave as though nobody is logged in.

This runbook uses tripwheel.app throughout. Substitute yours everywhere.

DomainServesProxies to
api.tripwheel.appBackend API127.0.0.1:5050
islandtours.tripwheel.appPublic site127.0.0.1:3000
dashboard.tripwheel.appDashboard (operators at /portal)127.0.0.1:3001
tripwheel.appTripwheel app / admin door127.0.0.1:3002
www.tripwheel.appredirect → apex—

Given that map, your shared cookie domain is:

COOKIE_DOMAIN=.tripwheel.app   # leading dot is required
Inconsistency in your own example files

frontend/.env.production.example sets the public site to www.tripwheel.app while backend/.env.production.example sets ISLAND_TOURS_URL=https://islandtours.tripwheel.app. Those cannot both be the public site. Pick one host for it and use that single value everywhere — this doc assumes islandtours.tripwheel.app. If you'd rather the public site own www, swap it consistently in all the places listed in the env reference.

02

Point DNS at the server

Do this before touching Caddy. DNS changes need time to propagate, and Caddy's certificate request fails if the name doesn't already resolve to your VPS.

Find your VPS IP

Hostinger shows it in VPS → Overview. It looks like 203.0.113.45.

Add these records

In your DNS panel (Hostinger Domains → DNS Zone, or wherever the domain's nameservers point):

TypeName / HostValueTTL
A@your VPS IP300
Awwwyour VPS IP300
Aapiyour VPS IP300
Adashboardyour VPS IP300
Aislandtoursyour VPS IP300

Use a short TTL (300 seconds) while you're setting up, then raise it to 3600 once everything works. If your VPS also has an IPv6 address, add the matching AAAA records with the same names.

Verify before continuing

on your laptop
dig +short api.tripwheel.app
dig +short dashboard.tripwheel.app
dig +short islandtours.tripwheel.app
dig +short tripwheel.app

Every one of them must print your VPS IP. If not, wait and retry — do not proceed.

Cloudflare users

If your domain sits behind Cloudflare, keep the proxy off (grey cloud) for now. The orange cloud adds a second proxy hop; the backend is configured to trust exactly one, so rate limiting would start counting Cloudflare's IP as every visitor. Let Caddy own TLS. Turn the proxy on later only if you also adjust the trusted-hop count in backend/src/main.ts.

Email DNS (needed for booking emails to arrive)

Transactional email goes through Resend. Add your domain in the Resend dashboard and paste the DKIM, SPF and DMARC records it gives you into the same DNS zone. Until that domain shows "verified", every booking confirmation, password reset and operator invite silently fails to send.

03

Prepare the VPS

Ubuntu 24.04 LTS. Everything below is run once, on a fresh server.

a. Log in and create a deploy user

Never run the apps as root.

ssh root@YOUR_VPS_IP
apt update && apt upgrade -y

adduser deploy                    # set a password when asked
usermod -aG sudo deploy

# copy your SSH key over so you can log in as deploy
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy/

Open a second terminal and confirm ssh deploy@YOUR_VPS_IP works before locking root out:

as root
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh

b. Firewall — only three ports

ufw allow OpenSSH
ufw allow 80/tcp        # Caddy: certificate challenge + http→https redirect
ufw allow 443/tcp       # Caddy: everything else
ufw --force enable
ufw status

Postgres, Redis and the Node processes are never exposed. They only listen on 127.0.0.1 or inside Docker's private network, and Caddy is the single front door.

c. Swap — stops builds getting killed

fallocate -l 4G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
free -h

d. Docker

curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy

Log out and back in as deploy so the group membership takes effect, then check docker ps runs without sudo.

e. Node 22 + pnpm 10 + PM2

These are for the Next.js apps — the backend never needs Node on the host, it ships inside its image.

as deploy
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs

sudo corepack enable
corepack prepare pnpm@10 --activate

sudo npm install -g pm2

node -v    # v22.x
pnpm -v    # 10.x

f. Caddy

sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl

curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
  | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg

curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
  | sudo tee /etc/apt/sources.list.d/caddy-stable.list

sudo apt update && sudo apt install -y caddy

caddy version

Caddy installs as a systemd service, already running and serving a placeholder page on port 80. You'll replace its config in step 7.

05

Generate every secret once

Several secrets must be identical across apps. Generate them all in one go, paste them into a scratch note, and copy from there — that's how you avoid a mismatch that produces no error, just silently broken behaviour.

run once, keep the output
echo "POSTGRES_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')"
echo "REDIS_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')"
echo "BETTER_AUTH_SECRET=$(openssl rand -base64 32)"
echo "TRAVELER_SESSION_SECRET=$(openssl rand -base64 32)"
echo "INTERNAL_API_SECRET=$(openssl rand -base64 32)"
echo "REVALIDATE_SECRET=$(openssl rand -base64 32)"
echo "ENCRYPTION_KEY=$(openssl rand -hex 32)"
echo "ADMIN_PASSWORD=$(openssl rand -base64 18)"
echo "SYSTEM_ADMIN_PASSWORD=$(openssl rand -base64 18)"

What the shared ones do, in plain terms:

SecretJobIf it doesn't match
INTERNAL_API_SECRET Lets the Next.js servers skip the API's per-IP rate limit while rendering pages Builds hit 429 mid-render; logged-in users get bounced
REVALIDATE_SECRET Lets the backend and dashboard clear the public site's page cache after a write Public site keeps showing yesterday's prices; no error anywhere
ENCRYPTION_KEY Encrypts Stripe keys and operator tokens stored in the database Changing it later makes every stored credential unreadable — set it once and never rotate casually
BETTER_AUTH_SECRET Signs staff/operator/admin login sessions Changing it logs everyone out
TRAVELER_SESSION_SECRET Signs traveller "look up my booking" tokens (deliberately separate) Booking-reference login links stop working
The backend refuses to boot without these

The API validates its environment at startup and throws a readable error listing exactly what's wrong. In production it hard-fails if INTERNAL_API_SECRET is missing. Secrets under 32 characters are rejected, and any value containing change-me is rejected as a leftover placeholder.

06

Deploy the backend

One docker compose up brings up Postgres, Redis and the API together. Migrations run automatically on every boot; seeding only when you ask for it.

a. The compose-level env file

/srv/tripwheel/island-tour-development/.env
cd /srv/tripwheel/island-tour-development
cp .env.example .env
nano .env
fill it in like this
POSTGRES_USER=island
POSTGRES_PASSWORD=<from step 5>
POSTGRES_DB=island_tours

REDIS_PASSWORD=<from step 5>

# Bind the API to loopback ONLY — Caddy is the front door.
# Without the 127.0.0.1 prefix, port 5050 is open to the whole internet.
BACKEND_PORT=127.0.0.1:5050
BACKEND_IMAGE_TAG=latest

# true for the FIRST boot only (creates the admin user), then set back to false
RUN_SEED=true

# Empty on purpose: switches off the temporary --trace-deprecation debug flag
NODE_OPTIONS=
Do not skip the 127.0.0.1

docker-compose.yml publishes ${BACKEND_PORT:-5050}:5050. Set BACKEND_PORT=5050 and Docker binds 0.0.0.0 — and Docker writes its own iptables rules, so UFW will not protect you. Your API ends up publicly reachable on port 5050 with no TLS. BACKEND_PORT=127.0.0.1:5050 expands to 127.0.0.1:5050:5050 and closes that hole.

b. The application env file

cp backend/.env.production.example backend/.env.production
nano backend/.env.production

07

Caddy: every domain, HTTPS automatically

This is the easy part. You write hostnames; Caddy obtains and renews the Let's Encrypt certificates itself, redirects HTTP to HTTPS, and keeps them valid forever. There is no certbot step and nothing to schedule.

Write the Caddyfile

sudo nano /etc/caddy/Caddyfile
/etc/caddy/Caddyfile
# Global options — the email Let's Encrypt uses for expiry warnings.
{
	email admin@tripwheel.app
}

# ── Backend API ───────────────────────────────────────────────
api.tripwheel.app {
	encode zstd gzip

	# Optional: keep the API docs off the public internet.
	# Swagger is served in production too. Delete these 3 lines to leave it open.
	@docs path /api/docs*
	respond @docs 404

	reverse_proxy 127.0.0.1:5050
	log {
		output file /var/log/caddy/api.log
	}
}

# ── Public traveller site ─────────────────────────────────────
islandtours.tripwheel.app {
	encode zstd gzip
	reverse_proxy 127.0.0.1:3000
	log {
		output file /var/log/caddy/islandtours.log
	}
}

# ── Operator + admin dashboard ────────────────────────────────
dashboard.tripwheel.app {
	encode zstd gzip
	reverse_proxy 127.0.0.1:3001
	log {
		output file /var/log/caddy/dashboard.log
	}
}

# ── Tripwheel marketing + admin login door ────────────────────
tripwheel.app {
	encode zstd gzip
	reverse_proxy 127.0.0.1:3002
	log {
		output file /var/log/caddy/tripwheel.log
	}
}

# www → apex, permanently
www.tripwheel.app {
	redir https://tripwheel.app{uri} permanent
}

Apply it

sudo caddy fmt --overwrite /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy

# watch certificates being issued
sudo journalctl -u caddy -f

Look for certificate obtained successfully once per domain. Then: 

curl -i https://api.tripwheel.app/api/v1/health

A 200 over HTTPS means the API, TLS and DNS are all correct.

Why Caddy needs no special tuning here

Three things nginx would have needed explicit configuration for, Caddy already does: it forwards X-Forwarded-For and X-Forwarded-Proto by default (so rate limiting sees real visitor IPs), it streams request bodies rather than buffering them (so Stripe webhook signature verification gets the raw bytes intact), and it imposes no request body size limit (so media uploads pass through). You don't need proxy_set_header, proxy_request_buffering off or client_max_body_size.

Ignore this file

deploy/nginx/island-api.conf exists in the repo from an earlier plan. You're on Caddy — leave it alone. Do not install nginx alongside; both want port 80 and the second one to start will fail.

08

Build and run the three Next.js apps

Same recipe three times: write .env.production, install, build, then let PM2 keep it alive.

The single biggest Next.js gotcha

Every NEXT_PUBLIC_* value is baked into the JavaScript at build time, not read when the server starts. The .env.production file must exist and be correct before you run pnpm build, and changing one of those values later means a full rebuild — restarting PM2 does nothing.

Also: delete any .env.local on the server. Next loads it in production too and it overrides .env.production, so a leftover dev file will quietly point production at localhost:5050.

a. Public site — port 3000

/srv/tripwheel/island-tour-development/frontend/.env.production
NEXT_PUBLIC_BACKEND_URL=https://api.tripwheel.app
NEXT_PUBLIC_SITE_URL=https://islandtours.tripwheel.app

# Server-only. Must equal the backend's INTERNAL_API_SECRET.
INTERNAL_API_SECRET=<same value as the backend>

# Server-only. Accepts a comma-separated LIST so you can rotate in two deploys.
# Must contain the value the backend and dashboard send.
REVALIDATE_SECRET=<same value as the backend>

# 'true' ONLY on the real production site — this fires live conversions.
NEXT_PUBLIC_ENABLE_TRACKING=true

# Optional
NEXT_PUBLIC_COOKIEBOT_CBID=
NEXT_PUBLIC_TRUSTPILOT_REVIEW_URL=

# Leave EMPTY. '1' exposes internal error detail to visitors.
NEXT_PUBLIC_ERROR_DEBUG=
cd /srv/tripwheel/island-tour-development/frontend
rm -f .env.local

A build that dies with Killed and no stack ran out of memory. Confirm swap is on (free -h), build the apps one at a time, and if it still fails cap the heap: NODE_OPTIONS=--max-old-space-size=2048 pnpm build.

Image optimization moved onto your CPU

No action needed at deploy time — sharp is an optional dependency of Next 16 and pnpm install already pulled it in. But be aware of what changed: on Vercel, resizing every tour photo was the platform's job. Here it is your VPS's, and the public site renders a lot of Cloudinary imagery. If CPU sits high under real traffic, see the recommendations section — the fix is to let Cloudinary do the resizing rather than to buy a bigger server.

09

Smoke test before you tell anyone

Most cross-app misconfiguration is silent. These checks make it loud.

  • https://api.tripwheel.app/api/v1/health returns 200.
  • https://islandtours.tripwheel.app loads and shows real tours (not an empty state).
  • https://dashboard.tripwheel.app/portal shows the operator login screen.
  • https://tripwheel.app loads; https://www.tripwheel.app redirects to it.
  • Log into the dashboard with ADMIN_EMAIL / ADMIN_PASSWORD — then reload the page. Staying logged in after a reload is what proves COOKIE_DOMAIN is right.
  • Open the browser console on the dashboard. Zero CORS errors means CORS_ORIGINS is right.
  • Edit a tour's price in the dashboard, save, then reload the public tour page. The new price appearing within seconds proves REVALIDATE_SECRET and REVALIDATE_TARGET_URL are right.
  • Trigger a password reset. The email arriving proves Resend + your DNS records are right.
  • Confirm port 5050 is not reachable from outside: from your laptop, curl --max-time 5 http://YOUR_VPS_IP:5050/api/v1/health must time out or refuse.
Two files that must stay in sync across repos

Neither of these fails to compile, so they only show up in production: lib/cache-tags.ts must be byte-identical in the dashboard and the public site (a drifted tag is rejected as unknown_tag at runtime), and the dashboard's lib/config/rbac.ts must mirror the backend's src/config/roles.config.ts or the dashboard mis-gates its own UI. Diff them after any deploy that touched either repo.

11

Working with the database directly

Postgres runs inside Docker with no published port — nothing on the internet can reach it. That's correct, and you don't have to give it up to get a GUI. Below: how to get a proper table browser without ever exposing the database.

a. Open a loopback port on the VPS (do this once)

Add a port mapping bound to 127.0.0.1. This makes Postgres reachable from the VPS itself only — still invisible to the internet, and still behind your firewall. It's what makes an SSH tunnel possible.

island-tour-development/docker-compose.yml → postgres service
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    ports:
      # Loopback ONLY. Never write '5432:5432' — that publishes it to the world,
      # and Docker's own iptables rules bypass UFW.
      - '127.0.0.1:5432:5432'
    environment:
      ...
docker compose up -d postgres

# confirm it is loopback-bound: the line must start with 127.0.0.1
docker compose ps postgres
sudo ss -tlnp | grep 5432
Never run docker-compose.dev.yml on the VPS

The dev stack in the same repo publishes Postgres as '5432:5432' — bound to all interfaces, with the default credentials island/island. It's written that way on purpose for laptop development. On a public server it is an open database. Always pass no -f flag on the VPS, so compose uses docker-compose.yml.

b. Tunnel it to your laptop

Run this on your Mac and leave the terminal open. It makes the VPS database appear at localhost:5433 on your machine — encrypted through SSH, with no open port anywhere.

on your laptop
ssh -N -L 5433:127.0.0.1:5432 deploy@YOUR_VPS_IP

Port 5433 on purpose — your Mac already runs Postgres 17.4 on 5432 for local development, and reusing it would silently connect your GUI to the wrong database.

d. Prisma Studio — the schema-aware option

A desktop client shows raw tables. Prisma Studio shows your model — relations are clickable, enums are dropdowns, JSON columns are formatted. Best for eyeballing a booking and its operator and its tour together.

with the tunnel from (b) still open, on your laptop
cd ~/devripon/tripwheel-x-islandtours/island-tour-development/backend

DATABASE_URL="postgresql://island:YOUR_PASSWORD@127.0.0.1:5433/island_tours?schema=public" \
  pnpm prisma studio

# opens http://localhost:5555
Prisma Studio writes are real writes

Studio bypasses every business rule the API enforces. Editing tier_key without also updating tier_rank, commission_tier and deposit_pct leaves a tour permanently mis-ranked; a confirmed booking with a null commission_amount is treated as data corruption and blocks conversion tracking. Use Studio to read. Make changes through the dashboard, and if you must write SQL, take a backup first.

e. Quick queries without any of the above

Sometimes you just want to check one number. SSH in and use psql directly:

  -c "SELECT status, count(*) FROM bookings GROUP BY status;"

Handy psql commands once you're in: \dt lists tables, \d bookings describes one, \q quits.

f. A browser-based GUI on a subdomain (convenient, but read this first)

If you genuinely want db.tripwheel.app in a browser from anywhere, run pgweb as a container on the internal network and put Caddy's basic auth in front. Understand the trade: you are turning a database that is currently unreachable into one that is one stolen password away. The SSH tunnel above is strictly safer, and only slightly less convenient.

add to docker-compose.yml
  pgweb:
    image: sosedoff/pgweb:latest
    restart: unless-stopped
    environment:
      PGWEB_DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}?sslmode=disable
    ports:
      - '127.0.0.1:8081:8081'
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - island-net
generate a password hash, then add the site to your Caddyfile
caddy hash-password
# prompts twice, then prints a $2a$... hash — copy it into the block below

The basic_auth directive below needs Caddy 2.8 or newer (it was spelled basicauth before). Check with caddy version; the apt repo in step 3 installs a current build.

	basic_auth {
		ripon $2a$14$PASTE_THE_HASH_HERE

Add an A record for db pointing at the VPS, then sudo systemctl reload caddy. Caddy issues the certificate automatically, as with every other host.

g. Should you use Neon instead?

Neon is managed Postgres in the cloud with its own web SQL editor and table browser — no tunnel, no container, nice branching for staging. It's a real option, but it changes the shape of this deployment:

Postgres in Docker (this guide)Neon
CostIncluded in the VPSFree tier, then monthly
Query latencySame machine — sub-millisecondNetwork hop per query; noticeably slower unless the region matches your VPS
GUITunnel + client (above)Built into their dashboard
BackupsYou set up the cron in step 10Automatic, point-in-time restore
Setup changeNoneMust edit docker-compose.yml

If you do switch: delete the postgres service from docker-compose.yml and remove the DATABASE_URL line from the backend service's environment: block, then put your Neon connection string in backend/.env.production instead. That override is the catch — leave it in place and compose will keep pointing the app at a Postgres container that no longer exists.

My recommendation

Stay on the Docker Postgres. This app is chatty with its database — booking flows, ranking jobs and page prerendering all issue many small queries — and same-machine latency is worth more here than a hosted SQL editor. Use the SSH tunnel plus TablePlus; it takes ten seconds to open and exposes nothing.

Redis, while you're here

The password lives in the compose .env, not in your shell — load it first, or redis-cli authenticates with an empty string and every command returns NOAUTH. 

cd /srv/tripwheel/island-tour-development
export $(grep '^REDIS_PASSWORD=' .env | xargs)

docker compose exec redis redis-cli -a "$REDIS_PASSWORD" ping        # PONG
docker compose exec redis redis-cli -a "$REDIS_PASSWORD" keys 'bull:*'

Those bull:* keys are the background job queues — nightly ranking, email sending, translations. If they're piling up and never draining, the worker side is stuck.

REC

Recommendations

Opinions, not instructions — what I'd actually do with this stack, in the order I'd do it. Each one says why, so you can disagree with the reasoning rather than just the conclusion.

Before you launch

1 · Keep Postgres in Docker; reach it by SSH tunnel

Don't move to Neon and don't put a database GUI on a public subdomain. This app is unusually chatty with its database — a single tour page issues many small queries, and the nightly ranking job walks the whole catalogue — so same-machine latency is worth more here than a hosted SQL editor. The tunnel from §11b takes ten seconds to open, exposes nothing, and gives you the same TablePlus window you'd get from a managed provider.

Revisit only if backups become the thing you keep forgetting. Neon's automatic point-in-time restore is a genuine advantage over a cron job you have to remember to test — but solve that by testing the cron job, not by moving the database.

2 · Add a healthcheck to the backend service

docker-compose.yml health-checks Postgres and Redis but not the API itself, so a backend that boots and then wedges still shows as Up and Docker never restarts it. One block fixes that:

docker-compose.yml → backend service
    healthcheck:
      test: ['CMD-SHELL', 'node -e "fetch(\'http://127.0.0.1:5050/api/v1/health\').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"']
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 60s

start_period: 60s matters — migrations run before the server listens, and without it a slow migration looks like a failing container.

3 · Take the backup off the server on day one

The cron job in §10 writes dumps to the same disk as the database it's dumping. That protects you from DROP TABLE and from nothing else. Add a second line that copies them somewhere else — Hostinger snapshots, an S3 bucket, rclone to Google Drive, anything off-box.

Then restore one into a scratch database before you launch. An untested backup is a guess. This is the single highest-value hour in this entire document.

4 · Keep Swagger closed

The @docs path block in the step-7 Caddyfile is written as optional. Make it permanent. Swagger is served in production by deliberate decision, which is fine on a private network and free reconnaissance on a public one — it publishes every route, every DTO field and the exact auth header names. You lose nothing: run the API locally when you need the docs.

5 · Set NEXT_PUBLIC_ENABLE_TRACKING=false anywhere that isn't production

That flag exists precisely because staging also builds with NODE_ENV=production. Get it wrong on a staging host and your test bookings land in real Google Ads and Meta conversion data, which is expensive to notice and worse to unpick. If you add a staging deployment later, this is the first variable to set.

First week

6 · Uptime monitoring on the health endpoint

UptimeRobot's free tier checking https://api.tripwheel.app/api/v1/health every five minutes is enough. Without it, the way you find out the API is down is an operator messaging you. Add a second check on the public site's homepage — the API can be perfectly healthy while PM2 has the storefront in a crash loop.

7 · Sentry, before you need it

Self-hosting means no platform error dashboard. When a traveller reports "checkout didn't work", your only evidence is pm2 logs and whatever scrolled past. The backend repo's ops guide has the setup steps in §8 — do it while things are calm, not while debugging.

8 · fail2ban and unattended upgrades

sudo apt install -y fail2ban unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades

Key-only SSH already blocks password brute-force; fail2ban stops the log noise and the wasted CPU. Unattended upgrades keep the OS patched without you scheduling it. Two commands, no ongoing cost.

9 · Watch disk, not just memory

Docker image layers accumulate on every --build, and Hostinger VPS disks are small. A full disk takes down Postgres in a way that reads like corruption. Monthly: 

df -h
docker system prune -af --filter "until=168h"   # images unused for a week

Not --volumes. Ever. That flag deletes postgres-data.

When traffic grows

10 · Push image resizing to Cloudinary before buying a bigger VPS

Next's image optimizer is the first thing to saturate CPU on a self-hosted storefront, and your images already live in Cloudinary — which resizes on delivery, for free, at the edge. Serving .../w_800,q_auto,f_auto/... URLs through a custom loader moves that work off your server entirely. Cheaper and faster than scaling the box.

11 · Scale vertically first, and stay single-instance while you do

Adding VPS RAM and cores is a reboot. Running a second backend instance is a project: the rate limiter counts in memory per process, and the BullMQ workers would need explicit concurrency control before two of them are safe. One well-sized server carries this workload a long way — take the reboot.

12 · Split the frontends off before you split the backend

If one VPS does stop being enough, move the three Next.js apps to a second box (or back to Vercel) and leave the API, Postgres and Redis together. The apps are stateless and trivially relocatable; the database is neither. Only two things change: the Caddyfile reverse_proxy targets become the new host, and CORS_ORIGINS stays exactly as it is — because it lists public origins, not machines.

If you only do three of these

Off-site backups that you have actually restored once (3), a healthcheck on the backend (2), and uptime monitoring (6). Those three turn "the site is down and I don't know why or for how long" into a solved problem. Everything else on this list is an optimisation.

Where this doc stops

This is the deploy-day runbook: get it live, correctly, once. For everything after that — rotating database and Redis passwords, restoring a backup, audit logs, Sentry error monitoring, OpenTelemetry tracing, tuning the rate limiter, scaling past one VPS — read technical-doc/06-operations/VPS-OPERATIONS-GUIDE.md in the backend repo.

Two places that guide diverges from this one, because it was written against the earlier plan: it assumes nginx in front (you're on Caddy — step 7 replaces its reverse-proxy and TLS instructions entirely) and it assumes the frontends live on Vercel (they're on this VPS under PM2 — step 8 replaces that). Everything it says about Postgres, Redis, backups and monitoring still applies as written.

Written against the repositories as they stand on 19 August 2026: backend NestJS 11 / Prisma 7 in Docker (Postgres 16, Redis 7), Next.js 16.2 with Cache Components on all three frontends. Ports 5050 / 3000 / 3001 / 3002 are pinned by the code, not incidental — the cache-revalidation wiring depends on the 3000 / 3001 split.
